# XATA Phase 3 — пакет изменений для Codex

## База для работы

Репозиторий: `neofart-art/cian`  
Ветка: `xata/initial-app`

Работать поверх актуального `HEAD` ветки на момент выполнения.

**Не выполнять deployment на OMV.**  
После изменений прогнать тесты, закоммитить результат в `xata/initial-app` и сообщить SHA.

Не выполнять destructive Docker/volume operations. Не менять persistent browser profile и не делать широких рефакторингов работающего browser collector без отдельного требования.

# 1. Новый логотип ХАТА

Эту задачу намеренно отложили из текущей итерации и переносим в отдельный пакет для Codex.

## Выбранная концепция

Использовать логотип в стиле:

- крупная оранжевая буква **«Х»**, одновременно формирующая силуэт крыши/дома;
- справа от верхней части «Х» — короткий вертикальный элемент, читающийся как труба/часть дома;
- под центром крыши — небольшое окно из четырёх квадратов;
- подпись **«ХАТА»** под знаком;
- первая буква **«Х»** в слове «ХАТА» — оранжевая;
- **«АТА»** — тёмно-графитовые;
- общий стиль: современный, лаконичный, без лишних деталей;
- фон логотипа должен быть прозрачным для production-asset.

Референс: выбранный пользователем оранжево-чёрный вариант из текущего обсуждения. Не использовать прежний бирюзовый вариант.

## Требования к production asset

Не встраивать изображение как огромный `data:image/...;base64` непосредственно в `index.html`.

Подготовить отдельный статический asset, предпочтительно:

```text
app/static/xata-logo.svg
```

Если SVG по технической причине не подходит, допустим оптимизированный WebP/PNG с прозрачным фоном.

Логотип должен:
- хорошо выглядеть на светлом текущем фоне XATA;
- не иметь белой прямоугольной подложки;
- оставаться читаемым при высоте 40–70 px;
- корректно масштабироваться на desktop и mobile;
- не раздувать HTML;
- не ломать CSP;
- не требовать внешних CDN/fonts/assets.

## Размещение

В верхнем левом углу страницы заменить текущую текстовую марку:

```text
ХАТА   Совместный поиск квартиры
```

на:

```text
[логотип ХАТА]   Совместный поиск квартиры
```

Подпись «Совместный поиск квартиры» сохранить.

На desktop ориентир:
- высота логотипа около 52–60 px;
- естественная ширина по пропорциям;
- вертикальное выравнивание по центру с подписью.

На мобильных:
- логотип уменьшать адаптивно;
- не допускать наложения на блок пользователя/кнопку выхода;
- при необходимости подпись можно скрывать по существующей логике.

## Favicon

Из знака логотипа сделать локальный favicon:
- использовать только символ «Х-дом/крыша» без подписи «ХАТА»;
- SVG или PNG;
- подключить в `<head>`.

## Cache busting

У проекта уже была проблема со stale static cache. Новый logo asset должен участвовать в действующей стратегии cache-busting/versioning. После deployment не должно требоваться ручное очищение кэша.

## Доступность

Для основного изображения:

```html
alt="ХАТА"
```

Если логотип обёрнут ссылкой на главную страницу, у ссылки должна быть понятная accessible name.

## Не делать

- не использовать inline base64 в HTML;
- не использовать внешние URL для логотипа;
- не использовать прошлый бирюзовый вариант;
- не менять всю цветовую схему сайта под логотип;
- не добавлять анимацию;
- не ухудшать текущую читаемость заголовка/авторизации.

## Tests / checks

Добавить или обновить проверки, которые подтверждают:
- asset существует;
- `index.html` ссылается на локальный asset;
- нет огромного inline base64 logo;
- логотип доступен HTTP 200 в тестовом приложении;
- CSP не блокирует asset;
- desktop layout не ломается;
- mobile layout не ломается;
- favicon подключён;
- существующие auth/UI тесты проходят.

# 2. Definition of Done для логотипа

Готово, когда:
- в шапке отображается именно оранжево-чёрный логотип ХАТА;
- используется отдельный локальный static asset;
- фон прозрачный;
- подпись «Совместный поиск квартиры» сохранена;
- favicon сделан из знака;
- desktop/mobile выглядят аккуратно;
- stale cache не мешает обновлению;
- полный relevant CI зелёный;
- deployment на OMV Codex самостоятельно не выполняет.

1. Закоммитить изменения в `xata/initial-app`.
2. Сообщить SHA.
3. Перечислить изменённые файлы.
4. Указать формат/размер logo asset.
5. Сообщить результаты тестов.
6. Дать безопасную пошаговую инструкцию обновления OMV:
   - backup SQLite;
   - backup `.env`;
   - `git pull --ff-only`;
   - config checks;
   - build только нужного `app`;
   - health check;
   - визуальная проверка desktop/mobile.
7. Deployment на OMV самостоятельно не выполнять.

# 4. Распознавание перепубликаций и дублей одного объекта

В процессе эксплуатации выяснилось, что продавцы и агенты часто снимают старое объявление с ЦИАН и публикуют практически то же самое заново под новым CIAN ID.

В результате один и тот же объект недвижимости может появляться в XATA несколько раз как разные объявления, хотя фактически это одна и та же квартира.

Нужно добавить отдельный слой идентификации **объекта недвижимости**, независимый от конкретного объявления ЦИАН.

## 4.1. Основная модель

CIAN ID больше не должен считаться идентификатором самой квартиры.

Нужно логически разделить:

- **listing** — конкретная публикация на ЦИАН с конкретным CIAN ID;
- **property/object** — реальный объект недвижимости, которому может соответствовать несколько listing.

Пример:

```text
Объект #37
├── CIAN 123456789 — старое объявление
├── CIAN 987654321 — перепубликация
└── CIAN 112233445 — новая перепубликация
```

Старые CIAN ID не удалять. Они должны оставаться в истории объекта.

## 4.2. Property group

Добавить внутренний стабильный идентификатор объекта, например:

```text
property_group_id
```

или отдельную таблицу `properties` с FK из `listings`.

Предпочтительно отдельная сущность `properties`, если это не усложняет миграцию чрезмерно.

Минимально:

```text
properties
- id
- created_at
- updated_at
- canonical_address
- canonical_area
- canonical_floor
- canonical_complex_name
- current_listing_id
- duplicate_confidence / metadata при необходимости
```

```text
listings
- id = CIAN ID
- property_id
- ...
```

Миграция должна быть data-preserving и идемпотентной.

## 4.3. Сопоставление нового объявления со старыми

При появлении нового CIAN ID сравнивать его не только с существующим ID, но и с уже известными объектами.

Использовать систему взвешенных признаков.

Базовый ориентир:

| Признак | Вес / влияние |
|---|---:|
| Полностью совпал нормализованный адрес | +40 |
| Площадь отличается не более чем на 0.3 м² | +20 |
| Совпал этаж | +15 |
| Совпал ЖК / complex_name | +10 |
| Описание сильно похоже | +10…15 |
| Цена отличается не более чем на 5% | +5 |
| Совпало метро | +3 |
| Другой этаж | −30 |
| Площадь отличается более чем на 2–3 м² | −30 |
| Другой дом / корпус | исключающий или почти исключающий признак |

Это не обязательно должна быть именно арифметическая сумма. Допускается более аккуратная rule-based реализация, но результат должен быть понятным и тестируемым.

## 4.4. Нормализация

Перед сравнением нормализовать:

- адрес;
- корпус / строение;
- номер дома;
- площадь;
- этаж;
- ЖК;
- метро;
- цену;
- текст описания.

Для текста:
- lower case;
- убрать лишние пробелы;
- убрать типовые маркетинговые фразы/шум при необходимости;
- не использовать HTML;
- сравнивать по устойчивому similarity score.

Не использовать внешний LLM/API для каждого объявления. Первая версия должна работать локально и детерминированно.

## 4.5. Уровни уверенности

Ввести три уровня:

### Автоматическое объединение

Если confidence >= 85%:
- считать новое объявление перепубликацией уже известного объекта;
- автоматически привязать к тому же `property_id`.

### Возможный дубль

Если confidence 65–84%:
- не объединять молча;
- показать пользователю:
  `Возможно, это перепубликация`;
- дать действия:
  - `Да, это тот же объект`;
  - `Нет, это другая квартира`.

### Отдельный объект

Если confidence < 65%:
- считать новым объектом.

Пороги вынести в константы/config, чтобы их можно было менять без переписывания алгоритма.

## 4.6. Что считать сильным совпадением

Адрес сам по себе недостаточен.

В одном доме могут одновременно продаваться несколько однокомнатных квартир одинаковой или близкой площади.

Наиболее надёжная комбинация:

```text
дом/корпус + площадь + этаж + описание
```

Дополнительные полезные признаки:
- ЖК;
- метро;
- цена;
- seller/agent identity, если ЦИАН стабильно отдаёт такие данные.

Другой этаж или другой дом должны сильно снижать вероятность совпадения.

## 4.7. Сохранение семейного статуса и оценки риелтора

Это ключевое требование.

Если старое объявление было:

```text
Понравилось
```

а продавец снял его и создал новый CIAN ID для той же квартиры, новая публикация не должна снова появляться как полностью новый неизвестный объект.

Нужно хранить на уровне property либо наследовать между listing:

- общий семейный статус;
- review metadata;
- мнение риелтора;
- комментарий риелтора.

Предпочтительный вариант:
- перенести пользовательские review/realtor поля на уровень `property`;
- listing остаётся историей публикаций.

Если это слишком рискованно для одной миграции, допустим промежуточный вариант с явным наследованием при confirmed match, но поведение для пользователя должно быть тем же.

## 4.8. История публикаций

Для каждого объекта хранить историю всех известных CIAN ID:

```text
05.10 — CIAN 123456789
11.10 — снято / перестало встречаться
12.10 — CIAN 987654321
18.10 — CIAN 112233445
```

Не удалять старые объявления физически.

Добавить минимум:
- first_seen;
- last_seen;
- статус текущей/исторической публикации;
- связь с property.

Можно считать listing неактивным, если он не встречался N успешных browser collection подряд или дольше заданного срока. Конкретную стратегию выбрать консервативно и тестируемо.

## 4.9. История цены

На уровне объекта желательно показывать историю цены по перепубликациям.

Пример:

```text
05.10   13 200 000 ₽
11.10   12 950 000 ₽
18.10   12 700 000 ₽
```

Минимально сохранять:
- дату наблюдения;
- listing ID;
- цену.

Если цена меняется внутри того же CIAN ID, это тоже должно попадать в историю.

Для этого допускается отдельная таблица:

```text
price_history
- id
- property_id
- listing_id
- observed_at
- price
```

Не создавать новую запись, если цена не изменилась.

## 4.10. UI

В основном списке не показывать несколько строк одного и того же объекта.

Показывать одну строку property.

В карточке/деталях объекта ненавязчиво показывать:

```text
Перепубликовано 2 раза
CIAN: 123456789 → 987654321 → 112233445
```

Если найден возможный дубль:
- отдельный badge;
- кнопка подтверждения/отклонения;
- не ломать текущие статусы и фильтры.

Для confirmed duplicate:
- новый listing не должен увеличивать счётчик `Новые объекты` как новая квартира;
- можно отдельно вести счётчик `Перепубликации`.

## 4.11. Фото как Phase 3 усиление алгоритма

Если browser collector уже получает или может безопасно получить URL фотографий без усложнения стабильной части коллектора, добавить фото-similarity как дополнительный сильный признак.

Предпочтительно:
- сохранять URL/идентификаторы изображений;
- вычислять perceptual hash (pHash/dHash/aHash) локально;
- сравнивать наборы фото между объявлениями.

Если совпадает несколько фотографий, это очень сильный признак того, что это тот же объект.

Важно:
- не хранить полноразмерные фото без необходимости;
- не делать тяжёлые downloads на каждый проход;
- кешировать результаты;
- не использовать внешний vision API;
- не ломать browser collector ради этой функции.

Если фото слишком рискованны для текущего пакета, реализовать их как отдельный optional sub-step после базового text/field matcher.

## 4.12. Возможный seller/agent fingerprint

Если в доступных данных стабильно присутствуют:
- seller ID;
- agent ID;
- название агентства;
- телефон/маскированный контакт;
- профиль продавца,

можно использовать их как дополнительный признак.

Не считать seller identity абсолютным доказательством, так как один агент продаёт разные квартиры.

Не сохранять лишние персональные данные без необходимости.

## 4.13. Ручное подтверждение

Для uncertain match пользователь должен иметь возможность подтвердить или отклонить связь.

Сохранять это решение, чтобы:
- повторно не задавать тот же вопрос;
- confirmed match не был разорван следующим auto-run;
- confirmed non-match не объединялся снова тем же алгоритмом.

Нужна отдельная фиксация manual decision / override.

Автоматический matcher не должен отменять ручное решение.

## 4.14. Regression safety

Не ломать:
- browser collection;
- CSV import;
- review statuses;
- realtor review;
- sorting;
- filters;
- XLSX;
- auth/roles;
- scheduler;
- existing SQLite data.

CSV import также должен проходить через duplicate/property matching, если в нём появляются объявления с новыми CIAN ID.

## 4.15. XLSX

В экспорт добавить при необходимости:
- property ID;
- текущий CIAN ID;
- все CIAN ID / количество перепубликаций;
- первая дата появления объекта;
- последняя дата появления;
- текущая цена;
- минимальная/максимальная замеченная цена;
- семейный статус;
- риелтор;
- duplicate confidence / manual confirmation при необходимости.

Не перегружать основной XLSX техническими колонками без пользы. Диагностические поля можно вынести в конец.

## 4.16. Tests

Добавить тесты минимум на:

### Exact / obvious duplicate
- новый ID;
- тот же адрес;
- та же площадь;
- тот же этаж;
- почти тот же текст;
- объединяется автоматически.

### Price changed
- тот же объект;
- цена отличается на 3–5%;
- остаётся тем же property.

### Slight text rewrite
- описание переформулировано;
- объект всё равно распознаётся.

### Same building, different apartment
- тот же адрес;
- другой этаж;
- не объединять автоматически.

### Similar area, different building
- близкая площадь;
- другой дом/корпус;
- не объединять.

### Ambiguous case
- confidence в промежуточной зоне;
- UI требует подтверждения.

### Manual override
- пользователь подтвердил match;
- следующий collection сохраняет связь.

### Manual reject
- пользователь отметил `это другая квартира`;
- auto matcher больше не объединяет эту пару.

### Review inheritance
- старый listing = liked;
- появляется новый ID того же объекта;
- property остаётся liked.

### Realtor inheritance
- статус/комментарий риелтора сохраняются при перепубликации.

### Price history
- новая цена создаёт новую запись;
- та же цена повторно не дублируется.

### Old CIAN IDs
- старый listing остаётся в истории;
- current listing обновляется корректно.

### Migration
- текущая production-like SQLite схема безопасно мигрирует;
- ничего не теряется.

## 4.17. Definition of Done

Функция считается готовой, когда:

- новый CIAN ID может быть распознан как перепубликация старого объекта;
- один объект имеет стабильный internal property ID;
- старые CIAN IDs сохраняются;
- основной UI не дублирует одну квартиру несколькими строками;
- liked/viewed/rejected сохраняются между перепубликациями;
- realtor status/comment сохраняются;
- цена имеет историю;
- obvious duplicates объединяются автоматически;
- ambiguous duplicates требуют ручного подтверждения;
- ручные решения имеют приоритет над matcher;
- разные квартиры одного дома не склеиваются по одному адресу;
- миграция production SQLite безопасна;
- CSV/browser flows продолжают работать;
- relevant tests зелёные.

## 4.18. Реализация по этапам

Если весь объём слишком велик для одного безопасного commit, Codex должен разбить работу минимум на:

### Step A — data model + deterministic matcher
- property entity;
- migration;
- normalized fingerprint;
- score/confidence;
- mapping listing → property;
- tests.

### Step B — UI + review/realtor inheritance
- одна строка на property;
- history CIAN IDs;
- manual confirm/reject;
- сохранение пользовательских статусов.

### Step C — price history
- запись изменений цены;
- UI/XLSX history summary.

### Step D — optional photo matching
- perceptual hashes;
- только если это можно сделать без риска для collector.

После каждого шага полный relevant CI должен оставаться зелёным.
