# Диагностика четырёх отсутствующих объявлений ЦИАН

Это расследование без повторного полного импорта. ID не добавляются вручную, не встраиваются в правила matcher/фильтров и не становятся исключениями. Сбор из реального ЦИАН и deployment на OMV из среды разработки не выполнялись.

## Установлено по текущему коду

До этого исправления collector выполнял один goto без прокрутки и пагинации. Это подтверждённое ограничение охвата, **не доказанная причина** пропуска четырёх квартир. Новый ограниченный обход описан ниже.

normalize_card требует корректный URL продажи квартиры на cian.ru. Ошибки SourceError/ValueError/TypeError/KeyError/AttributeError пропускают одну карточку. Площадь, этаж, адрес, метро, время пути, описание, фото и цена необязательны; отсутствие этих полей само по себе не исключает импорт. Цена берётся из видимого MainPrice/Price; не распознанная цена остаётся None. app/browser_source.py допускает price=None или price<=max_price. Локального исключения по площади/метро нет. Ошибочная высокая цена может привести к отклонению.

start_browser использует browser_criteria(), адаптер выбирает CIAN_SEARCH_URL либо source.search_url(). UI читает maxprice/foot_min из разрешённого URL, но подписи «Москва / вторичка / 1 комната» фиксированы. Переопределённый URL может им противоречить; фактическое environment OMV здесь неизвестно. Saved search без явных параметров нельзя признать соответствующим либо неправильным только по URL: сверяются видимые фильтры.

save_items сохраняет ID, связывает перепубликации с property. При ручном объединении старый ID остаётся в публикациях, текущий ID таблицы может отличаться. Действующие семейный/риелторский отказы помещают объект во свёрнутые «Не подходят» на «Все объявления». Выбранные остаются на обеих страницах; на «Наших» группа определяется последним состоявшимся просмотром. Клиентские поиск/фильтры могут дополнительно скрывать строку.

## Первый шаг на OMV: SQLite только для чтения, без обновления

Старый исходный каталог отсутствует: не начинайте с cd в него и не пересоздавайте контейнер ради диагностики. Найдите app по фактическому 172.31.1.1:3010->8000. Приватно проверьте mount существующего volume xata_xata_data в /data и DATA_DIR. Полный inspect содержит секреты; его нельзя публиковать. См. [восстановление конфигурации](OMV_RECOVERY_UPDATE.md), шаги до deployment.

scripts/diagnose_listings.py передаётся в существующий app через stdin, поэтому **пересборка для проверки DB не нужна**. Он открывает существующий SQLite с mode=ro, PRAGMA query_only=ON и BEGIN snapshot. Не импортирует app.main, не запускает migrations/scheduler/collect, не меняет решения, статусы и историю. По умолчанию сетевых запросов нет. При недоступном или несуществующем DB — ненулевой exit code; пустая DB не создаётся.

Получите файл из нового checkout проверенного SHA либо скачайте проверенный файл в новый каталог. Затем на OMV:

~~~sh
docker ps --format 'table {{.ID}}\t{{.Names}}\t{{.Ports}}'
umask 077
XATA_APP_ID='ПРОВЕРЕННЫЙ_ID_APP'
XATA_DIAGNOSTIC_SCRIPT='/АБСОЛЮТНЫЙ/ПУТЬ/К/НОВОМУ/checkout/scripts/diagnose_listings.py'
XATA_DIAGNOSTIC_REPORT='/АБСОЛЮТНЫЙ/ПРИВАТНЫЙ/КАТАЛОГ/xata-missing-listings.json'
docker exec -i "$XATA_APP_ID" python - 333859239 334907252 335066083 334090704 < "$XATA_DIAGNOSTIC_SCRIPT" > "$XATA_DIAGNOSTIC_REPORT"
chmod 600 "$XATA_DIAGNOSTIC_REPORT"
~~~

Смену DATA_DIR/имени файла учитывайте только по проверенным фактам: при необходимости добавьте --db /подтверждённый/путь/xata.sqlite3 после python -. Каталог отчёта должен уже существовать. Скрипт работает и с копией DB, не объявляя её автоматически production.

Для каждого ID проверяются listings, price_history, duplicate_candidates, identity_decisions, property_merge_audit, properties.current_listing_id и цепочки merged_into. Отчёт содержит first_seen/last_seen/last_imported/source, surviving property, текущий ID, все publication_ids, действующие коды оценок, последний просмотр, selection и ожидаемые разделы/свёрнутость без клиентских фильтров. Циклы, отсутствующий current pointer, неверный владелец и неполная legacy-схема не исправляются молча.

Проверяются публичные параметры CIAN_SEARCH_URL из runtime environment и их противоречия подписям UI; без override строится ожидаемый default URL по текущей reference policy репозитория. Код production-модулей, включая app/__init__.py, **не исполняется**. Runtime source fingerprints помогают сверить локальные правки генератора URL/адаптера; это не доказательство последнего реально отправленного запроса. Само предсказание раздела основано на текущих правилах репозитория и не доказывает состояние открытой вкладки.

Комментарии, пароли, cookies, HTML, DOM-тексты, полный search URL и произвольные query values не выводятся. Отчёт храните приватно. stored_listing_exists доказывает наличие записи. target_is_historical и current_listing_id показывают, под каким ID искать объединённую квартиру. Отсутствие строки **не доказывает**, что она не попадала в выдачу: прежние runs содержат агрегаты, не исторический per-ID trace.

## Дополнительно: уже открытый DOM, без поиска

В browser service подготовлен защищённый внутренним Bearer token POST /diagnostics/dom. Новый порт не публикуется. Используется тот же Chromium/context и общий lock. Он не вызывает goto/scroll/click/collect, не открывает страницы/закрытые API, не читает embedded state, cookies или токены. При занятости — 409; при login/challenge или поздней CAPTCHA targets пусты.

В ответе только запрошенные 1–20 ID и безопасные счётчики: видимые ссылки, индексы card nodes, предел 100, результат нормализации/тип ошибки, отсутствующие поля, разобранная цена и price-filter verdict, число нормализованных/уникальных ID, viewport и видимые признаки pagination. Индикатор next page не доказывает конец выдачи. Отсутствие ID в текущем DOM не доказывает отсутствие в полной выдаче или в прошлом запуске.

**Сейчас не обновляйте browser только ради этого шага. Сначала изучите DB-отчёт.** На старом сервисе endpoint может отсутствовать: будет endpoint_not_installed, без fallback на collect. Возможность подготовлена для отдельно проверенной установки диагностического кода после восстановления фактической конфигурации и при контролируемом отключённом расписании. Из Codex deployment не выполняется.

Если endpoint уже доступен и оператор подтвердил, что открыта нужная обычная выдача, к той же команде можно явно добавить --current-dom. Произойдёт ровно один запрос к внутреннему diagnostic endpoint с runtime token из env без его печати. Полный импорт и навигация не запускаются; редиректы с передачей token запрещены. Текущая страница могла измениться после последнего сбора: configuration.effective_request и current_dom.evidence.page_query относятся к разным моментам.

## После получения свидетельств

- ID сохранён: проверить текущий ID, merged chains, свёрнутый отказ и фильтры обеих страниц. Не сбрасывать оценки/ручные решения.
- Видимая ссылка есть, card selector нет: проверить реальную DOM-разметку этой пользовательской страницы.
- Индекс за лимитом, следующая страница либо карточка ещё не загружена: отдельно проектировать bounded pagination/scroll с сохранением ограничений и остановки на CAPTCHA, без исключений под четыре ID.
- normalization_error/rejected_price: сверить видимую цену и воспроизвести разбор на синтетическом fixture.
- ID отсутствует в DB и текущем DOM: стадия потери остаётся неизвестной; нужен разрешённый точечный просмотр выдачи, не молчаливое добавление квартир.

save_items/matcher и ручные решения не меняются. Повторный полный импорт не является диагностической командой.


## Точечная проверка фактического UI без запросов

scripts/diagnose_ui.js выполняется как DevTools Snippet **только на странице ХАТА**, не ЦИАН. После загрузки snippet вызовите в консоли:

~~~js
xataInspectListings(["333859239","334907252","335066083","334090704"])
~~~

Он читает уже загруженные records/rows и действующие функции поиска/разделов ХАТА, не делает fetch/refresh/import и не меняет оценки, фильтры, формы или DOM. Для найденного текущего/исторического ID показывает property/current ID, раздел, результат действующего поиска, hidden/connected/rendered и свёрнутый ancestor. Текст поиска, комментарии, адреса, HTML, cookies и токены не выводятся. На «Наших» отсутствие ID в загруженной подборке не означает отсутствие в БД. На незагруженной/неподдерживаемой версии возвращается ready:false. Сопоставляйте этот результат с read-only SQLite-отчётом для подтверждения именно фильтрации/свёрнутости в текущей вкладке.

UI snippet поддерживает и прежний загруженный интерфейс без listLoaded: непустые records подтверждают загрузку. Пустой legacy map остаётся ready:false, чтобы не повторять ложный вывод об отсутствии объявлений до первого ответа.


## Ограниченный обход выдачи

Collector теперь обрабатывает до 4 страниц, до 6 обычных прокруток к последней отображаемой карточке на страницу, до 100 уникальных объявлений на весь job. Общий hard deadline — 90 секунд, включая навигацию и readiness; app ждёт до 110 секунд. Между прокрутками — 0,5 секунды. Две последовательные лёгкие проверки без новых ID завершают прокрутку независимо от низа документа. Полный разбор повторяется только при появлении новых ID. Длинный footer не является основанием продолжать сбор на той же странице. Новые прокрутки прекращаются также после soft budget 6 секунд; уже начатое чтение имеет собственный timeout. Одна страница без новых ID после первой завершает обход. Новая навигация допускается только при запасе не менее 39 секунд: обычный timeout navigation 20 с, readiness 8 с, snapshot 3 с и резерв финальной проверки 8 с. При меньшем остатке — нормальная ограниченная остановка time_budget с обязательной финальной проверкой авторизации; это не ошибка и не свидетельство полного охвата. Истинный hard deadline 90 с и любая ошибка/CAPTCHA/logout по-прежнему отклоняют весь пакет. Если страница продолжает подгружаться позже этого окна, охват может остаться неполным.

Переходы выполняются только по видимой обычной ссылке «Следующая страница»/rel=next/PaginationNext. URL не синтезируется. Домен, путь и **все** query-параметры, кроме p/page, должны оставаться прежними, включая неизвестные служебные параметры. Изменение ограничений, неподдерживаемая кнопка без ссылки, повтор URL или лимит останавливают обход с явной причиной. Новые внешние API, страницы объявлений, embedded state и способы обхода защиты не используются.

Все карточки каждого снимка копируются одним синхронным DOM-вызовом; максимум 100 matching nodes за снимок сохранён. Скрытые/неисправные узлы пропускаются, отсутствующие необязательные поля допускаются. ID дедуплицируются между снимками и страницами. На CAPTCHA/login/ошибке любой страницы **весь текущий пакет** не импортируется, прежняя БД сохраняется. При обычном ограничении уже собранные записи возвращаются через прежний save_items; никаких специальных четырёх ID в правилах нет.

Статистика последнего запуска сохраняется в существующем JSON browser_state.coverage и доступна администратору в /api/state и /api/browser/status. Новых таблиц/миграций нет. Поля:
- pages, pages_detail (номер, новые ID, прокрутки и достижение scroll limit), scrolls, snapshots, progress_probes;
- matching_node_observations, normalized_observations, duplicate_observations — суммарные наблюдения, **не количество разных квартир**;
- unique_cards, dom_skipped_observations, normalization_errors, over_snapshot_limit_observations;
- rejected_price, admitted_missing_price, admitted — локальный фильтр адаптера после успешного сбора;
- stop_reason, incomplete, elapsed_seconds. exhaustive всегда false: отсутствие next link не доказывает исчерпывающий охват реального сайта.

stop_reason: no_next_link, no_new_ids, repeated_page, item_limit, page_limit, unsupported_next_control, unsafe_or_changed_pagination, login_required, confirmation_required, error, job_deadline, time_budget. Безопасные server logs содержат только счётчики, стадии и типы ошибок; без URL, HTML, cookies, query values или данных входа.

## Что подтверждено о параметрах OMV

По отчёту владельца: deal_type=sale, engine_version=2, foot_min=20, maxprice=14500000, object_type[0]=1, offer_type=flat, only_foot=2, region=1, room1=1. explicit_conflicts и unconfirmed_constraints пустые. has_unreported_parameters=true **не означает**, что неизвестные параметры являются фильтрами или причиной пропусков. Их названия и значения из отчёта неизвестны; они могут быть служебными. Нельзя объявлять их причиной или автоматически удалять. Фактическая авторизованная выдача и видимые фильтры требуют отдельной точечной проверки на OMV, без повторного полного импорта на этапе расследования.

## Обновление после отдельной проверки оператором

Не требуется устанавливать прежний диагностический коммит ради уже выполненной DB-проверки. Эта доработка затрагивает app (сохранение статистики) и browser (обход); для её применения потребуются оба образа. Compose, ports, volumes, профиль и SQLite schema не меняются. Старый каталог исходников на OMV отсутствует: сначала восстановить и сверить фактическую конфигурацию, локальные правки и резервные копии по [OMV_RECOVERY_UPDATE.md](OMV_RECOVERY_UPDATE.md). Не пересоздавать контейнеры только по устаревшим Compose labels. После проверки конфигурации использовать существующий project name, volume xata_xata_data и прежний .env; не включать расписание/полный сбор автоматически. Из разработки OMV не изменялся.

Реальный ЦИАН не проверялся. Синтетические Chromium-тесты проверяют lazy DOM, последовательные страницы, неизменность query constraints, повтор ID, CAPTCHA/HTTP error второй страницы и hard limits. Они не доказывают, что четыре объявления сейчас входят в выдачу или что реальные селекторы pagination соответствуют текущему ЦИАН.


## Подтверждённый запуск OMV 79aeb84a и исправление остановки

Владелец сообщил: pages=4, unique_cards=84, scrolls=59, stop_reason=job_deadline. В этом запуске 90-секундный hard deadline действительно отклонил весь новый пакет; авторизация сохранилась. Это объясняет отказ **этого запуска**, но не доказывает причину отсутствия четырёх конкретных ID в прошлых запусках.

В прежнем цикле no-new-ID stop был связан с достижением низа всего документа. При длинном footer продолжались одинаковые полные чтения карточек. Исправление разрывает эту связь: обычная прокрутка ориентируется на последнюю карточку, затем две проверки rendered DOM без новых ID переключают collector дальше. Progress читает только видимые публичные ссылки /sale/flat/ID/, не текст карточек, state, cookies или API. Full snapshot и нормализация повторяются только при новых ID; классификация CAPTCHA/login проверяется также при неизменных ID и перед завершением пакета.

pages_detail теперь содержит scroll_stop_reason (no_new_ids, empty, scroll_limit, scroll_time_budget) и elapsed_seconds. progress_probes отделены от snapshots: сравнивайте их, чтобы увидеть отсутствие повторного тяжёлого разбора. Общий timeout не увеличен; app/browser transport timeout, параметры поиска, профиль, объём БД и решения не менялись. Расписание остаётся под управлением прежнего environment; на OMV оно выключено и этой работой не включается.

## Отдельный случай 503 Chromium disconnected

Его исходная причина **не установлена**, отсутствие OOM само по себе не указывает на конкретную причину. Старый healthcheck называл любое исключение page.evaluate «Chromium disconnected», включая transient execution-context error во время навигации. Теперь health ping ограничен 3 секундами, различает failed probe и подтверждённое закрытие/краш page/context. Безопасные счётчики событий page_crash/page_close/context_close/browser_disconnect и page_closed/browser_connected доступны в authenticated /status.runtime и server logs. Для persistent context browser_connected может быть null; это отсутствие такого сигнала, а не доказательство disconnect.

На подтверждённой недоступности страницы readiness loop завершается сразу; временные ошибки живой страницы всё ещё повторяются в общем DOM deadline. Никакого автоматического удаления профиля, второго Chromium или сброса сессии нет. Прежний 503 задним числом эти новые сигналы не объясняют. На OMV пока ничего менять и повторять сбор не требуется. При будущей отдельно согласованной проверке сохранить время ошибки и безопасные события browser/container exit/health; не публиковать env, cookies, профиль или полный HTML.
