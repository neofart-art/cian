# Быстрая загрузка списков ХАТА

## Что меняется

- `/api/state?view=all`: все уникальные property, включая выбранные и свёрнутые отказы.
- `/api/state?view=ours`: только подборка; `totals.all/ours` остаются общими и не зависят от поиска.
- Оба ответа содержат краткие текущие данные, версии правок, диапазон цен, счётчики истории, все назначенные встречи и последний состоявшийся просмотр. Последний результат выбирается по фактическому моменту времени, включая старые ISO-даты с разными offsets/Z и микросекундами, без чтения старых заметок. Комментарии в списке ограничены 240 символами, впечатление последнего просмотра — 160.
- Полные тексты/истории одной квартиры: `GET /api/listings/{cian_id}/details`, с действующей авторизацией. Их запрашивают раскрытие истории/полного комментария, редактор и сравнение. Общий рекламный текст/DOM-текст не загружается вместе со списком. Старые открытые вкладки, запрашивающие прежний /api/state без view как same-origin browser request, получают явное требование обновить вкладку: нельзя передать короткий preview в старый редактор и затем сохранить его поверх полного текста. Действующие данные и черновики старой формы не заменяются таким ответом; перед перезагрузкой сохраните их. Обычные API-клиенты без Fetch Metadata сохраняют compact-default.
- Перед редактированием берётся полный комментарий: короткий preview нельзя случайно сохранить поверх исходного текста. После загрузки неизменённый развёрнутый комментарий не усекается новым summary.
- `/api/state?full=1` оставлен как явно запрошенный совместимый диагностический ответ. Интерфейс его не использует. Excel читает прежние полные данные; история и описания из SQLite не удаляются.
- Локальные пожелания включены в исходники: подпись «Риелтор», без «/ юрист»; без голубых строк и синих полос. Понравившиеся зелёные, отказы красные; метка подборки сохраняется на обеих страницах.

## До первого байта

Ранее endpoint читал все `l.*`, полные описания/DOM-тексты и истории, строил большой Python-объект, для каждого локального фото несколько раз вызывал `Path.resolve()`, затем FastAPI рекурсивно обходил весь результат через `jsonable_encoder` и сериализовал его. Это выполнялось до отправки заголовков; синхронный сбор histories и encoder занимали CPU, чтение/разбор больших SQLite TEXT и filesystem resolve добавляли задержку.

Новый список использует явную SQL-проекцию и агрегаты без чтения исторических текстов; `ours` ограничивается в SQL. URL локального фото формируется из строго проверяемого относительного имени без обхода файловой системы. Сам endpoint выдачи фото сохраняет проверки пути/границ каталога и прав доступа. JSON сериализуется один раз в явный Response, без рекурсивного конвертера FastAPI.

Добавлены безопасные логи `state built sql_ms=… assemble_ms=… serialize_ms=… queries=… json_bytes=… rows=…`. Они не содержат SQL, URL, текстов, cookies или секретов. Заголовок `Server-Timing` содержит `sql` (выполнение и получение строк запроса состояния), `assemble`, `serialize`, `gzip` и `app` (включая авторизацию). Время ожидания блокировки SQLite тоже попадает в SQL-замер. SQL авторизации в отдельном соединении входит в `app`, а не в `sql` состояния.

**Точные 5 секунд TTFB на OMV в CI не воспроизводились.** Установлены и измерены затраты прежнего кода; без нового Server-Timing непосредственно на OMV нельзя приписать все 5 секунд только SQL, CPU, диску или proxy. Замеры CI не являются прогнозом скорости Pentium G5400.

## Передача и опрос

JSON сжимается приложением gzip level 4 от 700 байт. Учитываются `Accept-Encoding`, `q=0`, wildcard и явное предпочтение identity; выставляются корректные Content-Length и Vary: Accept-Encoding. Уже закодированные ответы и изображения повторно не сжимаются. Ответы авторизации с CSRF-токенами не сжимаются. Авторизация проверяется и перед 304; `Cache-Control: no-store` сохранён.

Версия — постоянная пара epoch/revision в SQLite. AFTER INSERT/UPDATE/DELETE triggers охватывают объявления, property, цены, отзывы/комментарии, просмотры, подборку/этап, ручные решения и объединения, пользователей и состояние сборов. No-op UPDATE не меняет версию. Сессии и попытки входа не вызывают перезагрузку списка. Версия и данные читаются в одном snapshot. Слабый ETag учитывает пользователя, роль, страницу и full-режим; при совпадении сервер возвращает 304 с пустым телом и не строит список.

Фоновый опрос начинается через 5 секунд после завершения предыдущего; одновременно выполняется один state request. Скрытая вкладка отменяет текущий фоновый запрос и прекращает таймер. При возвращении проверяется версия. Принудительные обновления после действий выполняются последовательно; устаревший snapshot не перекрывает более новую сохранённую правку. Черновики/курсор комментариев и даты принадлежат стабильным DOM-элементам, не ответу опроса. Измерение высоты комментариев выполняется общим пакетом чтений до изменения кнопок: это исключает сотни последовательных перерасчётов layout таблицы. Ожидание state ограничено 20 секундами, details — 15; timeout показывает понятный повтор, данные не очищаются. История и сравнение продолжают работать.

До первого успешного ответа показано «Загрузка…». Первая ошибка оставляет эти подписи и кнопку «Повторить»; фоновая ошибка сохраняет строки и черновики, показывая сообщение о предыдущих данных. Нулевые счётчики и «ещё не было» показываются только после успешного ответа.

## Совместимость SQLite

Additive/idempotent `app/feed.py:migrate` добавляет только:

1. Таблицу `list_revision(id, epoch, revision)` с одной строкой.
2. Индекс `property_visits_latest(property_id,status,completed_at DESC,id DESC)`.
3. Собственные triggers `xata_list_revision_*`.

Таблицы не пересоздаются, столбцы/индексы/triggers пользователя, сессии и ручные решения не удаляются. Первоначальное заполнение подборки повторно не запускается. Collector, matcher, формула ипотеки, порты, Compose и volumes не менялись. Пересобирается только **app**.

## Проверки и воспроизведение

Полный workflow `.github/workflows/xata-checks.yml` выполняет Python regressions, Node, Compose в двух режимах, Chromium/WebKit, сборку обоих образов и offline headed/noVNC/profile smoke. Production и реальный ЦИАН не используются.

Дополнительно:

- `tests/test_feed.py`: 500 квартир с длинными текстами, scoped API, lazy details, отсутствие filesystem walk, gzip negotiation/raw bytes, 304/авторизация/no-store, invalidation всех видов правок, идемпотентная миграция и неизвестные BLOB/индексы/triggers.
- `tests/test_feed_ui.py`: обе страницы, 500 квартир/20 выбранных, Chromium и WebKit, 390/1440 px, медленный ответ/первая и фоновая 503, повтор, single flight, hidden tab, длинный комментарий риелтора/перезагрузка, lazy history, дата/черновик/«ОК». Остальные UI regressions включают 360/390/430/768/1440/1920 px, роли, календарь, повторные просмотры, сравнение, формы, поворот экрана.
- `tests/test_omv_snapshot.py`: проверка защитных условий backup без Docker и production.
- `scripts/benchmark_state.py`: один и тот же synthetic SQLite для неизменённого `21c0d7405fd2b849ca7db69057cd4f9bf46e362b` и нового кода, 500 property, 20 выбранных, по 13 цен, 3 состоявшихся поездки, 6 длинных исторических комментариев; локальные фото. Пять запросов дают медиану. SQL измеряется execution/fetch, Python-проекция, конвертация и сериализация отдельно; число filesystem resolve профилируется отдельно, с накладными расходами profiler. Замеры фаз отдельных запусков не следует механически суммировать с медианой HTTP.
- Реальный loopback HTTP ограничен 256 КиБ/с и задержкой 150 мс, включая передачу тела по частям. Это синтетическая сеть, не интернет OMV. Нагрузочные браузерные тесты используют отдельный настоящий HTTPS-сервер с self-signed тестовым сертификатом на loopback и тем же ограничением скорости/задержкой, чтобы Chromium и WebKit проверяли реальный HTTP 304/gzip. Прочие UI-тесты используют offline bridge. Физические телефоны не проверялись.
- Артефакты каждого полного CI: `xata-performance/performance.json` и `xata-ui-screenshots`. Итоговые цифры находятся в отчёте выполнения и JSON, а не закреплены как обещание скорости.

Локальное воспроизведение после установки зависимостей:

~~~sh
git worktree add --detach /tmp/xata-perf-base 21c0d7405fd2b849ca7db69057cd4f9bf46e362b
XATA_PERF_BASE_ROOT=/tmp/xata-perf-base python scripts/benchmark_state.py
python -m pytest -q
node --test tests/review_state.test.cjs
RUN_BROWSER_TESTS=1 python -m pytest -q tests/test_browser_dom.py tests/test_ui.py tests/test_comments_ui.py tests/test_feed_ui.py
~~~

Для проверки сохранения риелтора проверяйте POST /realtor-review: 200 и увеличенный realtor_version, затем /details после перезагрузки. Сервер по-прежнему требует актуальные property_id/realtor_version; отсутствие токенов даёт 422, чужая версия — 409, отсутствие прав — 403. Черновик и видимая ошибка сохраняются. Сообщённый сбой именно на OMV без его воспроизведения нельзя считать доказанно устранённым только по локальному тесту.

Инструкция при отсутствующем каталоге исходников: [OMV: discovery, backup, local changes, update and rollback](OMV_RECOVERY_UPDATE.md). Старые инструкции, начинающиеся с `cd` в удалённый каталог, к этому случаю неприменимы.
