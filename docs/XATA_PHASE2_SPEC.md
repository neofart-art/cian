Статус должен быть понятен не только по цвету: текстовая метка обязательна.

# 3. Исправить колонку «До метро»

Сейчас browser collector иногда записывает в `metro_time` не время маршрута, а время публикации/обновления объявления, например:

```text
4 часа назад сегодня, 13:25
вчера вечером, 19:14
```

Причина текущего кода: DOM `[data-name="TimeLabel"]` без проверки семантики может перекрывать корректный результат `parse_card_text()`.

## Требование

В поле `metro_time` допускается только реальная длительность пути до метро, например:

```text
7 мин. пешком
12 минут пешком
5 мин. транспортом
```

Не должны попадать:
- `сегодня`;
- `вчера`;
- `час назад`;
- `часа назад`;
- `минут назад`;
- время публикации;
- календарное/относительное время.

Если достоверно определить время до метро нельзя — хранить/показывать `NULL/—`.

## Реализация

Не доверять generic `TimeLabel` без валидации.

Допустимый подход:
- использовать `parse_card_text()` как консервативный источник;
- DOM-value принимать только если оно проходит явную проверку travel-duration;
- не позволять невалидному DOM `metro_time` перезаписывать корректное значение, извлечённое из текста.

Для пешего значения корректно заполнять `metro_walk_minutes`.

Изменения collector ограничить только этой задачей. Не трогать navigation, session, CAPTCHA/login detection, snapshot lifecycle, profile/noVNC.

## Очистка уже испорченных записей

Добавить безопасную одноразовую идемпотентную cleanup-migration:

Для существующих строк, где `metro_time` явно содержит relative publication time:
1. попробовать повторно извлечь корректное значение из сохранённого `card_text`;
2. если корректное значение найдено — заменить;
3. если не найдено — очистить `metro_time` и некорректный `metro_walk_minutes`;
4. корректные существующие значения не менять.

Добавить тесты на реальные проблемные строки вида «сегодня/вчера/N часов назад».

# 5. Сортировка по заголовкам таблицы

Сделать заголовки колонок интерактивными.

Поведение:

```text
первый клик  -> по возрастанию
второй клик  -> по убыванию
третий клик  -> вернуть стандартный порядок
```

Показывать рядом с активной колонкой небольшую стрелку `↑ / ↓`.

Сортировка клиентская по уже загруженным данным. Не делать отдельный API-запрос при каждом клике.

Сортировать «по смыслу»:

- `№ ЦИАН` — численно;
- `ЖК / адрес` — А→Я / Я→А;
- `Цена` — численно;
- `Площадь` — численно;
- `Этаж` — по номеру текущего этажа;
- `Метро` — А→Я / Я→А;
- `До метро` — по числу минут;
- `Добавлено` — по datetime;
- `Ипотека / мес.` — по рассчитанному платежу;
- `Статус` — по порядку `new -> liked -> viewed -> rejected`, и обратно;
- `Риелтор` — `не оценено -> одобрено -> отбраковано`, и обратно.

NULL/неизвестные значения при числовой сортировке размещать последними.

Стандартный порядок после третьего клика:

```text
new -> liked -> viewed -> rejected,
внутри группы first_seen DESC
```

Текущие быстрые фильтры по статусам должны продолжить работать совместно с сортировкой.

Кнопку ручного запуска поиска оставить только admin, но без редактируемых `price/metro` полей.

## Устранить текущую рассинхронизацию

Сейчас `CIAN_SEARCH_URL` открывает фиксированный поиск, а UI-параметры дополнительно влияют на локальный post-filter и сохраняются в последнем run.


- если задан `CIAN_SEARCH_URL`, безопасно извлекать `maxprice` и `foot_min` из его query для server-side Filters/display;
- если нужных параметров нет — использовать явно определённые безопасные defaults/config;
- клиент не должен присылать произвольный budget/metro для browser collect.

Изменение `.env`/search URL в будущем должно быть единственным местом, где владелец меняет реальные критерии.

Сам `CIAN_SEARCH_URL`, browser service и правила навигации на cian.ru не менять без необходимости.

# 14. Ипотечный платёж

Добавить колонку:

```text
Ипотека / мес.
```

Расчёт для каждой квартиры из её текущей цены.

Фиксированные параметры:

```text
Первоначальный взнос: 6 000 000 ₽
Ставка: 18% годовых
Срок: 15 лет
Схема: аннуитет
```

Не включать:
- страховку;
- комиссии;
- дополнительные банковские услуги.

## Формула

```text
principal = max(price - 6_000_000, 0)
monthly_rate = 0.18 / 12
n = 15 * 12 = 180

payment =
principal * monthly_rate * (1 + monthly_rate)^n
------------------------------------------------
           (1 + monthly_rate)^n - 1
```

Если:
- `price == NULL` -> показывать `—`;
- `price <= 6 000 000` -> `0 ₽/мес.`.

В UI показывать компактно:

```text
≈ 92 400 ₽/мес.
```

Для отображения можно округлять до ближайших 100 ₽, но сортировать по точному рассчитанному значению.

Платёж должен автоматически пересчитываться после изменения цены при очередном browser/CSV update.

Не обязательно хранить расчёт в SQLite: это derived value.

Добавить тот же расчёт в XLSX как отдельную колонку, чтобы экспорт отражал текущую инвестиционную оценку.
